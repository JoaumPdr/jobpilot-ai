## Decisões herdadas da F1-T02-a (confirmadas pelo JP em 2026-11-16)

- Rotas REST por `candidate_id`.
- `POST /skills` permitido: sem catálogo não há como vincular habilidade.
- Valores de `level` são os mesmos do CHECK do banco: `iniciante`, `intermediário`, `avançado`; `NULL` = desconhecido.
- `years` existe no vínculo (`candidate_skills.years`) e na experiência (`candidate_experiences.years`), ambos `>= 0`.
- Erros no formato `{error, message, request_id, details?}`; 404/409/422.

## Endpoints

| Método | Rota | Descrição |
|--------|------|-----------|
| `GET` | `/skills?q=` | lista/busca o catálogo (case-insensitive) |
| `POST` | `/skills` | cria habilidade canônica (409 se o nome já existir) |
| `GET` | `/candidates/{id}/skills` | lista as habilidades do candidato |
| `POST` | `/candidates/{id}/skills` | vincula por `skill_id` **ou** `canonical_name` (cria no catálogo se faltar) |
| `PATCH` | `/candidates/{id}/skills/{skill_id}` | atualiza nível/anos/evidência do vínculo |
| `DELETE` | `/candidates/{id}/skills/{skill_id}` | remove o vínculo (catálogo preservado) |
| `GET` | `/candidates/{id}/experiences` | lista experiências |
| `POST` | `/candidates/{id}/experiences` | cria experiência |
| `PATCH` | `/candidates/{id}/experiences/{experience_id}` | atualiza campos enviados |
| `DELETE` | `/candidates/{id}/experiences/{experience_id}` | remove experiência |

`GET /candidates/{id}` passa a incluir `skills` e `experiences` (mudança aditiva no `CandidateRead`).

## Contratos

- `SkillCreate`: `canonical_name` (1–200, obrigatório), `category` (opcional, texto livre até a F2-T01), `aliases` (lista de strings).
- `CandidateSkillCreate`: exatamente um entre `skill_id` e `canonical_name`; `level` opcional (enum); `years` opcional `>= 0`; `evidence_note` opcional.
- `CandidateSkillUpdate`: `level`, `years`, `evidence_note` opcionais; `null` limpa o campo.
- `ExperienceCreate`: `company` e `role` (1–200), `start_date`, `end_date?`, `description?`, `skills_used` (lista, default `[]`), `years?` (`>= 0`); `end_date >= start_date`.
- `ExperienceUpdate`: todos opcionais; `null` em `company`, `role`, `start_date` ou `skills_used` → 422; `end_date: null` = vínculo atual. A faixa de datas é revalidada no serviço combinando os valores atuais com os enviados (`InvalidDataError` → 422).

## Regras de negócio

- Candidato inexistente → 404 em qualquer rota aninhada.
- Skill inexistente por `skill_id` → 404; por `canonical_name` → cria no catálogo.
- Par candidato/skill duplicado → 409 (pré-checagem + índice único do banco).
- Nome canônico duplicado → 409, comparando sem diferenciar caixa (o banco é case-sensitive; a API fecha a lacuna).
- Remover vínculo/experiência inexistente → 404.
- Nenhuma rota faz `select` ou commit; serviços não importam FastAPI.

## Plano de testes

- **Unitários:** criar skill e conflito; vínculo por nome cria catálogo; duplicata; 404 de skill/candidato; PATCH limpa campos; PATCH de experiência com data inválida → 422; combinação de datas com valores atuais.
- **API:** fluxo completo candidato → skill → vínculo → experiência; validações (nível, anos, datas); 404/409/422 padronizados; remoção de vínculo/experiência; `GET /candidates/{id}` com listas.
- **Sem rede e sem LLM.**

## Riscos

- `CandidateRead` maior (mais joins) — usar `selectinload` para evitar N+1.
- Duplicidade de nome canônico é case-sensitive no banco; a API compara em minúsculas, mas concorrência ainda pode criar variações de caixa (registrado para a F2-T01).
- A regra de datas no PATCH combina estado atual + payload; depende de o serviço ler antes de gravar.
