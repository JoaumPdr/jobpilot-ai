## Proposta de endpoints (a confirmar antes de implementar)

Como o MVP é single-user, mas as tabelas já são multiusuário, a proposta é REST por `candidate_id`:

| Método | Rota | Descrição |
|--------|------|-----------|
| `POST` | `/candidates` | cria candidato (e preferências opcionais) |
| `GET` | `/candidates/{candidate_id}` | detalhe do perfil |
| `PATCH` | `/candidates/{candidate_id}` | atualiza dados do candidato |
| `DELETE` | `/candidates/{candidate_id}` | remove candidato (CASCADE) |
| `GET`/`PUT` | `/candidates/{candidate_id}/preferences` | lê/substitui preferências (upsert 1:1) |
| `GET`/`POST` | `/candidates/{candidate_id}/skills` | lista/víncula habilidade (`skill_id` ou `canonical_name`) |
| `PATCH`/`DELETE` | `/candidates/{candidate_id}/skills/{skill_id}` | atualiza/remove vínculo |
| `GET`/`POST` | `/candidates/{candidate_id}/experiences` | lista/cria experiência |
| `PATCH`/`DELETE` | `/candidates/{candidate_id}/experiences/{experience_id}` | atualiza/remove experiência |
| `GET`/`POST` | `/skills` | catálogo de habilidades (necessário para vincular) |

**Dúvida 1:** manter rotas REST multiusuário (`/candidates/{id}`) ou um atalho `/profile` single-user que resolve o candidato único? (Recomendo REST + `/profile` como alias opcional só se você quiser.)

## Decisões de desenho propostas (confirmar)

1. **Camadas:** `app/schemas/profile.py` (ou um arquivo por entidade), `app/repositories/profile.py`, `app/services/profile.py`, `app/api/routes/profile.py`. Rotas não importam modelos; serviços não importam FastAPI.
2. **Erros:** `app/core/errors.py` com exceções de domínio (`NotFoundError`, `ConflictError`) e handlers que devolvem `{error, message, request_id}`; `RequestValidationError` → 422 com `details`; `HTTPException` preservada.
3. **E-mail:** o schema aplica `EmailStr` + normalização (trim/lowercase); o serviço garante unicidade e traduz `IntegrityError` em 409/422 com mensagem clara.
4. **JSONB (estrutura proposta — confirmar):**
   - `education`: lista de `{institution, degree, field_of_study?, start_date?, end_date?, description?}`.
   - `languages`: lista de `{name, level}` com `level` em `básico|intermediário|avançado|fluente|nativo`.
   - `aliases`: lista de strings; `skills_used`: lista de strings.
   - `knockout_rules`: objeto com chaves conhecidas (a definir) — por ora validar como objeto JSON.
5. **`years`:** validar `>= 0` também em Pydantic (além do CHECK do banco), nas duas tabelas.
6. **Preferências:** `PUT` substitui o conjunto (idempotente) e cria a linha se não existir.
7. **Habilidades:** vincular por `skill_id` existente **ou** `canonical_name` (cria no catálogo se não existir); duplicata do par retorna 409.
8. **Experiências:** `end_date` nula = vínculo atual; validar `end_date >= start_date` no schema (além do CHECK).
